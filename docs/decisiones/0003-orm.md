# 0003. ORM: Drizzle

- **Estado:** Aceptada (Fase 0)
- **Fecha:** 2026-09-21
- **Referencias:** especificación §57, §58, §94, §95, §96

## Contexto

El §95 ordena elegir el ORM en la Fase 0 buscando: buen soporte de PostgreSQL, migraciones
reproducibles, transacciones, restricciones e índices, `DECIMAL` sin pérdida y bloqueo cuando haga
falta. Añade que la elección **no puede degradar las reglas financieras**.

## Método

Prueba de concepto descartable (fuera del repositorio) contra el PostgreSQL 17.10 local, con los
mismos cinco escenarios para cada candidato y su flujo real de migraciones:

| #   | Escenario                                                                                  |
| --- | ------------------------------------------------------------------------------------------ |
| T1  | `NUMERIC` sin pérdida: importe `9007199254740993.01` (> 2^53) y cuota `1.954800`           |
| T2  | Transacción con rollback completo                                                          |
| T3  | `SELECT … FOR UPDATE`: dos gastos concurrentes de 60 sobre un saldo de 100 (uno debe fallar) |
| T4  | `CHECK (available >= 0)` definido por el ORM y activo en la base de datos                  |
| T5  | Índice único parcial: una sola etapa `ACTIVE` por proyecto (§86)                           |
| T6  | Migración generada, aplicada, y segunda generación sin deriva                              |

## Resultados

| Criterio                               | Drizzle 0.45.3 (+ kit 0.31.11) | Prisma 7.10.0                  | TypeORM 1.1.1                    |
| -------------------------------------- | ------------------------------ | ------------------------------ | -------------------------------- |
| T1–T5                                  | 5/5                            | 5/5                            | 5/5                              |
| `NUMERIC` devuelto como                | `string`                       | objeto `Decimal` (decimal.js)  | `string`                         |
| `CHECK` en el esquema                  | Sí                             | **No** (SQL manual)            | Sí                               |
| Índice único parcial en el esquema     | Sí                             | **No** (SQL manual)            | Sí                               |
| `FOR UPDATE`                           | API tipada (`.for('update')`)  | **SQL crudo**                  | API (`pessimistic_write`)        |
| T6 (deriva)                            | Sin cambios                    | Sin deriva (tolera SQL manual) | Sin cambios                      |
| Formato de migración                   | SQL legible                    | SQL legible                    | Clase JS con SQL (`--esm`)       |
| Detección de cambios sin base de datos | Sí (instantáneas)              | Requiere BD sombra             | Requiere BD real                 |
| `npm audit` (dependencias de la PoC)   | 4 moderadas (herramientas)     | **4 altas** (CLI)              | 0                                |
| Tamaño instalado                       | 26 paq. / 60 MB                | 109 paq. / 325 MB              | 40 paq. / 32 MB                  |
| Módulo oficial de NestJS 12            | No (proveedor propio)          | No (proveedor propio)          | Sí (`@nestjs/typeorm` 12.0.1)    |
| Versión estable                        | 0.x (1.0 en RC)                | 7.10 (CLI `latest` apunta a RC 8) | 1.x                           |

También se comprobó que los tipos de Drizzle compilan con **TypeScript 6.0.3 estricto y
`nodenext`**, y que el compilador rechaza asignar un `NUMERIC` a `number` o usar columnas
inexistentes.

## Decisión

Adoptar **Drizzle ORM** (`drizzle-orm` 0.45.3 y `drizzle-kit` 0.31.11, versiones exactas) con el
driver `pg`.

## Justificación

1. **Las invariantes financieras viven en el esquema.** `CHECK`, índices únicos parciales y
   bloqueos se declaran en código tipado y generan SQL revisable. En Prisma esas reglas quedan
   como SQL escrito a mano fuera de su modelo, precisamente donde el proyecto más las necesita.
2. **Dinero como cadena por diseño.** `NUMERIC` llega como `string` y el compilador impide tratarlo
   como `number`, alineado con el §94 (los decimales viajan como cadenas).
3. **Migraciones SQL reproducibles y revisables**, sin necesitar la base de datos para detectar
   cambios (útil en CI). Las reglas que un ORM no modela (p. ej. disparadores que impidan editar
   `audit_logs`, §35) se añaden como migraciones SQL personalizadas.
4. **SQL explícito para el dashboard.** Series temporales, agregaciones del ledger y ventanas se
   expresan con un constructor cercano a SQL y tipado.
5. **Encaja en una pila solo ESM.** Sin decoradores ni metadatos de reflexión en las entidades,
   evita los problemas conocidos de TypeORM con relaciones circulares en ESM.
6. **Ligero y con superficie de dependencias pequeña**, frente a Prisma (325 MB y 4 vulnerabilidades
   altas en su CLI).

## Riesgos y mitigaciones

- **Aún no es 1.0** (la 1.0 está en RC). *Mitigación:* versiones exactas fijadas; todo acceso a
  datos encapsulado en repositorios/servicios propios (nada de consultas Drizzle en controladores);
  migración a 1.0 planificada como tarea explícita cuando sea estable.
- **Sin módulo oficial de NestJS.** *Mitigación:* un `DatabaseModule` con un proveedor propio
  (`Pool` de `pg` + `drizzle`), unas pocas líneas.
- **Plan B validado:** TypeORM 1.1.1 con `EntitySchema` superó los mismos escenarios y tiene módulo
  oficial de NestJS; sería la alternativa si Drizzle presentara inestabilidad.

## Reglas de uso (obligatorias desde la Fase 1)

- Columnas de dinero y cuotas: `numeric(precision, scale)` y **nunca** modo `number`.
- Las restricciones (`CHECK`, únicos parciales, claves foráneas) se declaran en el esquema.
- Las operaciones que gastan saldo bloquean la fila de la casa (`.for('update')`) y revalidan dentro
  de la transacción (§40), además del `CHECK` como última barrera (§58).
- Toda migración se genera con `drizzle-kit`, se revisa y se versiona; nunca se edita una migración
  ya aplicada.
- Las pruebas de integración usan `letfer_test` con PostgreSQL real.
